# 서버 권위를 유지하는 계산 분담 검토

2026-09-28. 서버 `8de93f8`, 클라이언트 `8cc4e72` 기준. 게임 코드는 변경하지 않고 서버 복사본에서 기존 벤치마크와 CPU 프로파일을 실행했다.

**후속 반영:** 아래는 변경 전 구조를 검토한 기록이다. 이후 서버의 빈 땅 시야 계산을 제거하고, 주변 아군의 거리·차폐로 실제 적 유닛의 공개 여부만 판정하도록 구현했다. 같은 조건의 500유닛 전체 틱은 3.097 → 0.992ms로 줄었다. 현재 구조와 검증 결과는 [전장의 안개 문서](fog-of-war.md)를 따른다. 아래의 시야 stamp·칸 중심·빈칸 생성 관련 설명은 이전 구현에 해당한다.

클라이언트가 맡을 수 있는 것은 화면 계산과 서버가 검증할 수 있는 제안이다. 실제 위치·속도·충돌·피해·자원·적 공개 여부는 서버가 결정해야 한다. 현재 이미 외형 계산 대부분이 클라이언트에 있으므로, 당장의 CPU 절감은 서버 시야 계산 범위를 줄이는 쪽이 더 유망하다.

## 현재 계산 비용

Intel Core i7-6700K, Windows, 실제 168×92 맵, 500유닛, 2진영, 수신 큐 2개. 기존 `BenchmarkFogFullTick/500`을 200틱씩 반복했다. 유닛은 공격 이동하며 표본 수 유지를 위해 체력을 높인다. 이 벤치마크에는 실제 소켓 쓰기·대기, 플레이어 명령 폭주, 다수 일꾼의 채집, 실행 중 새 웨이브 생성이 포함되지 않는다. 따라서 실서비스 동접 한도나 모든 장면의 비용으로 해석하면 안 된다.

- 프로파일 없는 3회 평균: 3.277 / 3.200 / 3.175ms/틱. 중앙값 **3.200ms**.
- 같은 3회의 최대 틱: 16.82 / 15.03 / 16.03ms.
- 별도 CPU 프로파일: 200틱 × 10회, CPU 표본 총 6.79초.

| 시야 생성 `updateVision` | 73.20% | 서버 `fog.go:33` |

비중은 각 함수가 호출한 하위 함수 비용을 포함한다. 전체 장면에 대한 보장이나 해당 함수를 제거했을 때의 정확한 절감률은 아니다. 프로파일 실행 중 최대 52.18ms인 틱도 한 번 관측했다. 원인은 이 자료만으로 확정할 수 없다. 프로파일 자체도 비용을 추가하므로 일반 측정과 구분했다. 평균 외에 긴 틱의 빈도와 단계별 비용을 추적하는 것이 좋다. 측정 방법은 [Go 공식 진단 문서](https://go.dev/doc/diagnostics)의 CPU 프로파일 설명을 참고했다.

길찾기는 별도의 기존 벤치마크로 측정했다. 본진 간 탐색은 1회 평균의 중앙값 약 **0.735ms**, 도달 불가능한 목적지는 약 **4.406ms**였다. 후자는 다른 장애물 배치의 합성 맵이다. 일반 틱 프로파일에서 A*가 두드러지지 않았어도 집단 이동 명령이나 도달 불가능한 목적지가 많을 때는 비용이 커질 수 있다.

관련 클라이언트 구현은 `maps/FogOfWar.cs`, `maps/FogLightMesh.cs`, `maps/MapWorld.cs`, `units/WorkerAnimation.cs`, `units/UnitDeathEffect.cs`, `buildings/Building.cs`다. 서버는 포탑의 명중·피해를 즉시 계산하고, 클라이언트 `Building.PlayShot`이 짧은 궤적만 만든다. 현재 서버에는 넘겨줄 투사체 비행 시뮬레이션이 없다.

### 이동 보간

`units/Unit.cs:58`의 `ApplyServerPosition`은 받은 좌표를 바로 `GlobalPosition`에 넣는다. 우선 서버의 20Hz 판정과 전송을 유지하면서, 클라이언트에 짧은 스냅샷 버퍼와 시간 정보를 넣어 표시만 부드럽게 만드는 것이 안전하다.

보간이 안정되면 위치 전송만 10Hz 같은 낮은 빈도로 실험할 수 있다. 서버 이동·충돌·전투·시야 판정은 계속 20Hz로 수행한다. 서버가 확정한 위치와 화면에 그리는 위치를 분리하고, 정지 시 마지막 위치를 반드시 전달해야 한다. 시간 기준은 서버 틱 번호/시각으로 맞춘다. 적 재등장·숨김·사망은 별도 즉시 이벤트로 처리하여 HIDE 뒤에 보간 버퍼의 적이 다시 그려지지 않게 한다.

전송 빈도 감소가 전체 CPU를 같은 비율로 줄이는 것은 아니다. 이번 표본에서 위치 메시지 처리는 약 0.44%였고 실제 소켓 쓰기는 측정하지 않았다. CPU 절감보다 움직임과 통신량 측면의 후보다.

### 검증 가능한 경로 제안

안전한 구조는 “이 위치로 이동했다”는 결과를 받는 것이 아니라, “이 경유점들로 이동하고 싶다”는 요청을 받는 것이다. 서버가 자기 상태를 기준으로 검사한 경로만 `pathFollower`에 넣고, 매 틱 실제 이동은 계속 서버가 수행한다.

검증에는 소유권·현재 명령 번호, 서버의 현재 시작 위치, 맵 범위와 유한한 좌표, 경유점 수·총 거리·검증 비용 제한, 유닛 몸 크기를 포함한 전 구간 통과 가능 여부, 장애물 변경 여부가 필요하다. 이동 속도와 유닛 간 충돌도 서버가 계속 적용한다. 클라이언트가 주장하는 도착 시각·속도·최종 좌표는 채택하지 않는다.

기존 `Grid.LineClear`는 선분을 1/4칸 간격으로 검사하는 근사 함수다. 현재는 서버의 실제 이동 충돌이 이를 보완한다. 이 함수 하나만으로 임의 경로의 완전한 안전성을 보장한다고 간주하면 안 된다. 검증 구간과 실제 이동의 충돌 검사를 함께 유지해야 한다.

잘못되거나 오래된 경로는 버리거나 제한된 서버 탐색으로 대체한다. 악성 제안을 무조건 A* 재계산으로 바꾸면 공격자가 서버 계산을 늘릴 수 있다. 경로가 없거나 응답이 늦은 클라이언트도 서버 처리 범위 안에서 게임이 계속되어야 한다.

플레이어가 선택하는 이동 경로라면 통과 가능한 여러 경로를 허용할 수 있다. 게임이 정확히 같은 최단 경로 선택을 규칙으로 요구한다면 단순 통과 검사만으로는 충분하지 않다. 우선 내 유닛의 명시적인 이동에 한정하고, 미니언의 경로·추격·자동 공격·자동 채집 결정은 서버에 유지하는 것이 적합하다. 숨겨진 적 상태를 경로 계산을 위해 클라이언트에 전달해서는 안 된다.

## 서버에 유지해야 하는 판정

- 실제 위치, 이동 속도, 지형·건물·유닛 충돌 및 밀어내기. 이는 사거리·길막·도착 시각에 영향을 준다.
- 공격 대상의 적법성, 사거리, 공격 주기, 피해, 사망.
- 채집 시간·대상·자리 점유, 운반량, 반납·자원 증가.
- 미니언 생성·자동 행동과 포탑의 표적 선택.
- 적 유닛을 공개할지 결정하는 시야와 UNIT/HIDE/POS/STATE/HP 필터링.
- 명령의 소유권·형식·빈도와 처리 비용 제한.

클라이언트 안개 표시를 믿고 모든 적 좌표를 보내면 화면 표시를 변경한 클라이언트가 적을 읽을 수 있다. 클라이언트가 보내는 “보이는 적 목록” 역시 서버 판정을 대체하지 못한다. 맵 해시 일치는 파일 호환성 확인이지, 클라이언트 코드가 정직하다는 증명이 아니다.

## 지금 먼저 적용할 서버 최적화

### 1. 시야의 중복 계산 줄이기

`game.go:121`과 `fog.go:163`에서 행동 전·이동/사망 후 시야를 각각 계산한다. 매번 모든 시야 제공자의 반경 안 칸을 DDA로 검사한다. 전송 직전 계산은 마지막 정찰병이 죽은 틱의 정보 노출을 막으므로 단순히 삭제하면 안 된다.

두 가지 후보를 별도로 측정할 가치가 있다.

1. 정지한 건물·유닛의 차폐 결과 재사용. 실제 위치, 반경, 진영, 장애물 상태가 그대로면 결과를 재사용한다. 칸 내부 이동도 모서리 시야를 바꾸므로 좌표를 칸 번호로만 묶는 캐시는 현재 규칙과 같지 않다. 여러 아군의 시야를 합치고, 제공자가 사라졌을 때도 올바르게 제거해야 한다.
2. 필요한 칸만 서버에서 조회. 운영 코드의 `isVisible`은 현재 `canTeamSee`를 통해 유닛 위치를 확인할 때 사용되고, 건물은 전역 공개다. 모든 빈 땅의 시야를 먼저 채우는 대신 적 유닛이 있는 칸에 대해 근처 아군이 볼 수 있는지를 검사하고, 같은 계산 단계의 결과를 재사용할 수 있다. 전체 안개 그림은 이미 클라이언트가 만든다. 현재 규칙을 유지하려면 목표를 서버 격자 칸 중심으로 판정하고 건물 자기 몸체 제외·시작 칸·대각선 규칙도 유지해야 한다. 밀집 전투에서는 후보 쌍이 늘어날 수 있어 항상 더 빠르다고 단정할 수 없다.

기존 서버의 `grid.blockVersion`은 **막힐 때만** 증가한다(`grid.go:18`, `SetBlocked`, `RemoveSolidRect`). 나무 제거·건물 파괴 시 시야가 열리는 변경은 이 번호로 감지할 수 없다. 시야 캐시에는 열림과 막힘 모두 증가하는 별도 장애물 변경 번호가 필요하다. 새 틱의 생성·접속 해제·사망 등도 반영해야 한다.

위 후보는 아직 구현하거나 절감률을 검증한 것이 아니다. 기존 차폐·대각선·공유 시야·마지막 정찰병 사망·재등장 테스트의 결과를 유지하면서 비교해야 한다.

### 2. 유닛 공간 분할

`separation`과 `bumpsEnemy`는 매 유닛마다 전체 `g.units`를 순회한다. 이번 표본에서는 합계 약 15.46%이고 규모가 커질수록 부담이 증가한다. 주변 칸의 유닛만 후보로 찾는 공간 그리드를 서버에 두면 권한을 넘기지 않고 계산을 줄일 수 있다. 적 탐색·포탑 탐색에도 같은 자료구조를 이용할 수 있다.

유닛 반지름을 포함한 검색 범위와 이동 단계 중 위치 갱신을 정확히 처리해야 한다. 근처 칸 경계의 충돌 후보를 빠뜨리면 실제 이동 규칙이 바뀐다. `gathererCounts`와 `nearestResource`에도 반복 순회가 있으나, 이번 측정은 채집 시나리오가 아니므로 비용 순위는 별도 측정이 필요하다.

### 3. 불신 클라이언트에 대한 연산 예산

현재 한 명령당 64유닛, 한 틱당 총 1024이벤트 제한은 있지만 연결별 명령 빈도 제한은 보이지 않는다. 한 클라이언트가 반복 MOVE/GATHER 등으로 공용 처리 시간을 차지할 수 있다. 연결별 처리 예산과 중복 이동 명령 합치기 등을 검토하되, 서로 다른 명령의 순서는 보존해야 한다.

`navigate.go:92`는 A*를 시작하기 전에 예산을 확인하고, `FindPath`가 끝난 뒤 탐색 수를 차감한다. `pathfind.go:74`의 탐색 루프 자체는 남은 예산에서 중단하지 않는다. 즉 20,000노드 제한은 엄격한 중단 상한이 아니다. 특히 도달 불가능한 경로의 반복 요청을 고려하면, 탐색 내부 예산과 다음 틱으로 넘기는 처리도 필요하다. 이것은 클라이언트 경로 제안 도입 여부와 무관하게 서버에서 해결할 문제다.

## 권장 진행 순서

1. 서버의 시야 결과 재사용 또는 필요한 칸만 조회하는 구현을 비교한다. 현재 측정에서 가장 큰 비용이다.
2. 서버의 유닛 공간 분할과 연결별 명령 예산을 적용한다.
3. 클라이언트 이동 보간을 넣고, 위치 전송 빈도 감소를 별도로 실험한다.
4. 집단 명령·복잡한 맵에서 길찾기 비중이 커지면 내 유닛의 검증 가능한 경로 제안을 검토한다.

실행한 벤치마크는 모두 통과했다. 이번 작업은 코드 구조 검토와 성능 측정이며, 게임 기능 변경이나 전체 회귀 테스트 실행은 하지 않았다. 측정 복사본과 원자료는 클라이언트의 `.godot/server-authority-review/`에 있다.
